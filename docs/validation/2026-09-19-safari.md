# Safari compatibility investigation — September 19, 2026

## Scope and reproduction

The investigation targets current desktop Safari. The available machine runs macOS 26.6.2 with Safari 26.6.2. Automated browser checks use Playwright 1.63.0 and WebKit 26.6. The original report did not include a Safari version or a specific error, so the findings below distinguish reproduced application failures from device qualification.

Before production changes, all 22 existing browser tests passed in WebKit. These exercise rendering, calibration with synthetic hands, gameplay, hand-loss pauses, powers, disconnect/reconnect, audio synthesis, and real same-origin MediaPipe worker inference. The deployed Vercel build also reached hand alignment with a synthetic video stream in WebKit, initialized the GPU delegate, and had no page errors or failed HTTP responses during startup.

## Root causes and fixes

The follow-up report supplied a concrete failure: camera connection succeeded in desktop Safari, but hand detection never became usable. Native Safari with the physical 640×480 camera reproduced it. `requestVideoFrameCallback` fired repeatedly with `metadata.mediaTime = 0`, while `video.currentTime` advanced normally. In one sample, 441 model results arrived at about 11 ms age, but `CameraSession` accepted only the first and rejected the remaining 440 as duplicate media timestamps. The UI stayed at “WAITING FOR FRESH CAMERA.” This was a timestamp-ordering failure, not slow inference or camera permission denial.

`FrameScheduler` now uses the advancing video clock when callback media timestamps stop advancing. If neither clock advances, the callback is still discarded. Capture timestamps and the existing 150 ms freshness and result-ordering checks remain unchanged. The unit regression first failed with `[0, 0, 0]` and passes with `[0, 20, 40]`, including a check that a truly repeated frame is skipped.

After this fix, native Safari accepted 897 of 897 results with no dropped frames and 17.4 ms average capture-to-result age. A later physical-hand sample showed one detected hand, 1,608 accepted results, no drops, and progression from alignment into reach calibration. These observations establish that the physical camera, bitmap transfer, GPU model, result acceptance, and hand controller all operated together; complete gameplay verification is recorded separately below.

### Native Safari end-to-end verification

A separate native Safari run used the upper hand from the attributed `tests/fixtures/woman_hands.jpg` photograph as a canvas camera stream. The real worker, GPU model, frame scheduler, controller, and application remained in use. Callback metadata was deliberately forced to zero to retain the original Safari failure condition; only the image position changed to follow the calibration prompts.

Observed phases were `landing → loading → align → reach-left → reach-right → playing → results`. The game recorded **650 points and 16 seconds of active gameplay**, including a Wide power-up, before the stationary test paddle missed the ball. The diagnostic sample contained 602 accepted results, 20.8 ms mean capture-to-result age, and no model errors. The visible HUD reported one detected hand and active tracking. This provides native Safari end-to-end evidence with photographed input; the physical webcam check above establishes the hardware capture path separately.

### Follow-up regression results

- 216 unit/integration tests passed, including the zero-metadata regression.
- All 24 WebKit browser tests and the 23 pre-existing Chromium browser tests passed. The photographed-hand regression covers the real model and both calibration steps with zero metadata timestamps.
- The first combined run also attempted that new test in Chromium and failed at `#hands-count`. A separate diagnostic found 47 successful hand detections but zero accepted frames under SwiftShader; default headless Chromium likewise detected hands but accepted none. Its software GPU exceeds the game's 150 ms freshness bound (standalone inference measured 168–204 ms). This Safari-specific regression is now explicitly skipped in the Chromium project. The existing Chromium real-worker and lifecycle tests remain enabled, and the production freshness bound is unchanged.
- The final `npm run test:browser -- tests/browser/hand-camera.spec.ts` run exited successfully: one WebKit pass and one explicit Chromium skip.
- Type checking, ESLint, Prettier, whitespace checks, production build, and all seven runtime/model asset hashes passed. The existing large Three.js chunk warning remains.

The local test server remains available at `http://127.0.0.1:5174/`. The changes have not been committed, pushed, or deployed.

The initial compatibility pass also addressed:

1. **Audio activation blocked camera startup.** `InvaderBreakApp.enable()` awaited `AudioDirector.activate()` before requesting the camera. That call can wait indefinitely for `AudioContext.resume()`. WebKit has a [reported Safari/PWA resume hang](https://bugs.webkit.org/show_bug.cgi?id=291892); a controlled never-settling audio activation reproduces the application's loading deadlock. Audio now starts from the same user click but completes independently of camera startup. Rejection degrades to visual cues, and stale completion cannot reopen the camera or update a newer session's status.
2. **The audio failure notice disappeared.** Startup wrote a sound-unavailable message directly into the camera status element, but the next HUD update overwrote it. The application now retains audio availability in state and renders the warning while the camera is active.
3. **Safari's engine was absent from routine verification.** Playwright ran only Chromium, including Chromium-specific launch flags in the shared configuration. WebKit is now a separate project; Chromium flags apply only to Chromium. The default browser command runs both engines.

## Native Safari smoke check

The installed Safari was also tested through its visible UI, without WebDriver or webcam access. Run `npm run dev -- --port 4175 --mode test --strictPort`, open `http://127.0.0.1:4175/tests/fixtures/safari-smoke.html` in Safari, and use the game's normal camera controls. The fixture substitutes only the video source with a canvas capture stream, imports the real application, and observes native worker messages. It is not included in the production entry.

Observed sequence in Safari 26.6.2:

1. Enable reached `align`, selected the GPU delegate, and returned more than 200 real hand-inference responses with zero page/worker errors. Blank video correctly detected no hands.
2. Disconnect returned to `landing` with `CAMERA OFF` and one stopped stream.
3. Enable again created a second stream, returned to `align`, and continued inference; the cumulative response count exceeded 1,100 with no errors.
4. Switching to another tab and back produced `suspended`, `CAMERA OFF`, and a second stopped stream, with an explicit Reconnect camera action.
5. Reconnect created a third stream and resumed GPU inference without errors. Final disconnect left all three streams stopped and `CAMERA OFF`, after 3,003 cumulative inference responses. The local test tab was then closed.

The fixture's `hands` counter counts worker inference responses, not detected hands. It verifies the real scheduler, bitmap transfer, GPU model, rendering, and lifecycle in Safari; it does not establish physical hand detection quality or latency.

## Limits and Safari requirements

- Safari needs a secure origin (HTTPS or localhost), camera permission, WebGL 2, and worker OffscreenCanvas/WebGL. [Safari 17 added OffscreenCanvas WebGL on macOS Sonoma 14](https://webkit.org/blog/14445/webkit-features-in-safari-17-0/); use an up-to-date Safari on that OS or newer. Older Safari/macOS combinations are not qualified by this change.
- `safaridriver` refused to create a session because **Allow remote automation** is disabled in Safari Settings → Developer. The native smoke check used Safari's visible UI instead; no Safari security setting was changed.
- [Playwright WebKit is a separate build](https://playwright.dev/docs/browsers#webkit), not the installed Safari browser. Passing its tests does not establish physical-camera performance, Safari permission UI behavior, or iPhone/iPad support.
- The follow-up physical-camera check established hand detection and progression to reach calibration after the timestamp fix. A sustained session should also complete calibration, play with one and two hands, disconnect/reconnect, and switch away/back. Verify that the camera stops on leaving and that audio and tracking recover after explicit reconnect. Full motion-to-photon latency and a sustained play session remain device qualification work.
